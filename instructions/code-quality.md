# 实现质量与缺陷治理通用细则

## 共享范围与权限边界

- 任何非平凡功能实现或缺陷修复，以及新增、修改、重构或审查生产代码、工具或脚本时必须读取本文件；纯文档、纯美术资源或只改序列化数值且不触及行为时不必读取。
- 用户当前明确要求和消费项目根 `AGENTS.md` 决定产品范围、验证、提交、发布及破坏性操作权限。本文件只统一实现质量与缺陷治理，不自行扩大任何权限。
- 项目专项细则可以按真实领域事实补充或收紧本文件，但不得用项目惯例静默保留重复权威、错误职责或新旧双轨。若条款仍无法同时满足，在相关写入前列出冲突并请求用户决定。
- 追求“最小且完整的改动”，不是最少行数或最少文件。可以为闭合当前受影响生产链而重构直接相关代码，不得借质量治理改造无关模块。

## 权威、职责与数据流

- 修改前先明确入口、唯一权威 owner、producer、不可变数据或状态产品、生命周期与状态迁移、consumer/执行边界、错误暴露及验证路径；这些关系不清楚时不得直接增加字段、分支、guard 或补偿。
- 同一事实只能有一个权威来源。消费者不得自行推导、修正或覆盖 producer 本应提供的状态；确需缓存时必须定义失效、刷新和生命周期归属。
- 配置所有权必须与行为所有权一致。由某个组件、策略或配置对象独占消费并决定行为的权重、比例、阈值、标签和策略列表，应由该 owner 或其显式引用的专用配置持有；全局设置只保存真正跨实例、跨变体统一的不变量。
- 判断资格、权限、存在性、状态或策略时，直接消费权威 owner 有意暴露的契约。不得用无关 tag、命名、目录、层级、容器成员、全局设置、UI 状态、生命周期信号或偶然副作用代理该事实。
- 一个类型、组件或方法保持单一功能级职责与一致抽象层级。独立状态、权限、生命周期、策略、失败模式或变化原因应形成职责命名的协作者；只拆文件、region、转发方法或薄 wrapper 不构成职责分离。
- 依赖通过明确引用、参数、接口或权威数据产品表达。不得新增隐藏全局查找、无 owner 的 singleton/service locator、静态可变状态、跨层偷取内部状态或依赖调用顺序的隐式耦合。

## 通用路径、特判与无用组件

- 功能、修复和内容接线默认复用现有权威正常路径。只改变输入数据、显示内容、配置或素材而不改变 owner、生命周期与处理语义时，必须让新情况沿既有 producer、产品与 consumer 链执行；禁止为单个 Prefab、Asset、consumer、状态或内容另建专用组件、独立 Prefab、renderer、updater、serializer、旁路或同义分支。
- 只有可证明存在独立的领域语义、owner、生命周期、状态迁移、权限、数据形态、交互/渲染契约或失败语义时才允许特判。素材不同、尺寸不同、当前只有一个 consumer、不熟悉现有 API、实现方便或不想触及现有链都不是依据；特判只能放在产生真实差异的决策边界，差异结束后的公共处理必须重新汇入同一权威链。不得为了消灭表面分支而合并职责不同的 owner。
- 在当前任务已经审计或修改的 producer/consumer、Prefab、Scene、工具或序列化链内，若组件没有任何当前运行时、Editor、authoring、序列化、Prefab 继承、测试或公开扩展契约 consumer，也不拥有独立状态、生命周期、配置、视觉、交互或工具职责，则它属于完全无用组件，必须在同一任务直接删除，并同步删除其专用字段、引用、序列化数据、Prefab 节点、Asset、注册和测试；不得保留 disabled 空壳、无引用脚本、薄 wrapper、占位节点或只为该组件存在的资源。
- “以后可能要用”必须有当前可指出的具体证据，例如用户已明确的后续需求、已发布且真实受控的扩展契约、必须保留的序列化/authoring 边界、框架硬契约，或已有明确 activation owner 与配置的暂未启用产品能力。通用名称、看似可复用、历史上存在、以后也许有 consumer、重建成本或单纯不确定都不是保留证据；没有当前职责且只有假想未来价值的组件应在真正需求出现时再实现。保留时必须能指出 owner、具体 consumer 或 activation 边界，不能只写模糊 TODO。
- “发现即删”与本文件的范围边界同时生效：当前受影响链内的完全无用组件清理属于闭合实现，不算无关重构；仅在搜索中发现且位于当前未授权系统的对象不得借此扩大修改范围，只报告其证据。任何删除仍不得越过用户数据、外部公开契约、破坏性操作和消费项目根规则的权限边界。

## 直接契约、无防御实现与状态精简

- 写代码、实现功能、修复、重构和代码审查时，完全摒弃 fail-close、防御性代码和 fallback。每项能力只能有一个由权威 owner 生产并由 consumer 直接执行的正常路径；项目惯例、历史事故、输入“可能为空”、调用顺序“可能不对”或“保险起见”都不能授权第二路径。
- 禁止新增或保留用于掩盖契约违例的判空/合法性 guard、`catch` 后继续、静默 return/disable、默认对象或默认值、自动 clamp/修复、重试、旧缓存、备用 route/实现、降级模式、紧急模式、兼容 wrapper 或“主路径失败再试另一条”的分支。真实产品选择必须由权威 owner 建模为互斥契约，不能以主路径失败为触发条件。
- 前置条件、合法输入和生命周期顺序由创建它们的 producer、caller 或配置 owner 一次保证；consumer 不重复防御。契约被破坏时在最初可归因边界直接暴露带 owner、输入和阶段的异常、断言、失败测试或公开错误，不得转换为安全输出、禁用行为、替代结果或额外状态。审查发现 guard/fallback 时，先修正能产生违例的上游 owner 与迁移，再删除该分支及其测试、字段和序列化数据，不能把 guard 本身当修复。
- 状态默认先删后加。可从权威产品推导、复制另一字段、只记录 `has/isReady/didFail/fallbackUsed`、只服务 guard/重试/恢复、或只为跨层手工同步而存在的字段、flag、enum case、缓存、snapshot、pending mode 和生命周期阶段必须删除。保留状态必须对应不可推导的真实产品事实，并能指出唯一 writer、创建事件、consumer 和退出迁移；否则不构成必要状态。
- 资源释放、订阅闭合和用户明确授权的外部操作边界仍由其生命周期 owner 负责；它们不能被扩写成生产功能的防御分支、备用结果或失败后继续执行路径。

## 类型与文件结构

- 每个手写 C# `.cs` 文件只能声明一个顶层类型；`class`、`record`、`struct`、`interface`、`enum` 和 `delegate` 均计入。访问级别、file-local、泛型、同一 namespace、类型很短或只被相邻类型使用都不构成同文件第二个顶层类型的例外；独立顶层类型必须各自进入职责命名文件。
- 唯一顶层类型内部可以声明 nested class/record/struct/interface/enum/delegate。嵌套类型必须确实从属于外层 owner 的实现或契约；拥有独立职责、生命周期、权限、变化轴或外部 consumer 时仍应提取为独立顶层类型和文件，不能把嵌套当成规避单顶层类型或职责拆分的容器。
- 每个手写 `class` 或 `record class` 的完整声明跨度不得超过 1500 个物理行；从属于该类型的 attribute、注释、空行、预处理分支和全部嵌套类型都计入，嵌套 class 自身也单独受 1500 行上限约束。不得通过一行塞入多条语句、删除必要可读性、增加 region、嵌套容器或移动声明来规避计数；达到上限前若职责已经分裂，仍须按职责提前提取。
- 手写生产代码、工具和测试禁止新增 `partial` 类型（`class`、`struct`、`record` 或 `interface`），也禁止向既有手写 `partial` 类型新增或搬入字段、方法、分支、状态、策略及生命周期职责。不得通过在多个 `partial` 文件之间移动代码满足单文件行数、复杂度、组织或审查门禁；所有声明必须枚举并按一个类型聚合审查其总行数、状态、依赖、权限、生命周期、入口和消费者，任何按文件统计的门禁也必须同时检查聚合类型。
- 当前任务需要改变既有手写 `partial` 类型时，先从完整受影响链提取职责命名的协作者、组件或不可变产品，并同步迁移对应字段、方法、入口、生命周期和消费者，删除旧状态与旧路径后再实现新行为。原类型只能保留自身职责内的最小编排，禁止用转发 wrapper、空壳 `partial` 或保留共享可变状态制造表面拆分；这项迁移只覆盖当前受影响链，不授权重写无关模块。
- 只有编译器、代码生成器或框架硬契约明确要求时才允许 `partial`；必须能指出生成源和硬契约，禁止手改生成文件，手写部分仍须保持单一职责。允许的 `partial class`/`record class` 按一个类型聚合所有人工维护声明计算 1500 行，生成输出不得成为继续塞入手写职责的理由。工具支持 `partial`、团队习惯、文件过长或便于分类均不构成例外。项目细则可以进一步禁止例外、降低行数上限或限制整个文件长度，但不得放宽单顶层类型、1500 行 class 上限或手写 `partial` 禁令；发生冲突时以共享门禁为准。
- 新增手写 C# 文件或修改既有类型的声明、状态、行为和结构时必须满足本节。若任务触及的既有文件含多个顶层类型，先把各类型移入独立文件；若触及的 class 已超过 1500 行，先从当前受影响链提取真实职责，再实现新改动。仅修正文档、注释或格式且不改变类型声明与行为时，不因此获得全仓清理授权；未触及的历史违规留待其首次相关修改时治理。

## 状态、控制流与生命周期

- 状态优先通过删除可推导字段和收敛唯一 owner 精简；只有确实存在多个不可推导且互斥的产品事实时，才用领域类型、枚举、不可变产品或显式迁移表达。不得用更多布尔开关、`null` 哨兵、隐含阶段或防御 mode 包围一个本可由 producer 保证的契约。
- 主路径应能顺序阅读，条件分支表达真实且互斥的领域决策。深层嵌套、重复条件、布尔参数驱动多模式或一个方法同时解析、决策、变更和表现，是重新审查职责与状态模型的信号。
- 契约定义的创建、取消、销毁、重载和对象复用生命周期必须闭合；订阅/退订、注册/注销、创建/释放、租用/归还及异步启动/取消由明确 owner 成对完成。不得为不属于产品契约的空、失败或禁用情形额外制造生存状态。
- 错误由最初能归因的 owner 保留输入和阶段后直接传播；只有公开契约本身声明的错误结果才作为一等结果返回。不得空 `catch`、吞异常、静默返回默认值，或让 consumer 补判空、补合法性和继续执行。
- 不得用任意延迟、重复调用、重试、隐藏元素、关闭反馈、刷新多次、参数调节或临时遏制掩盖时序、所有权和状态错误。

## 可观测性、数学化与性能预判

- 观测能力属于缺陷链。现有异常、Console、trace、Gizmo、报告或工具输出若不能无损复现输入、关联各阶段或定位首个错误边界，必须暂停依赖这些缺口的诊断，先修最窄权威观测 producer，并完成该观测契约所需的最窄验证；不得把“信息不足”降为备注、TODO、人工猜测或长期散落的临时日志。
- 面向人的 Console 摘要可以舍入，但必须携带稳定、可检索的 transaction/evidence ID。权威结构化证据必须保留因果相关数值的 round-trip 表达、单位、坐标系、owner、revision/context、阶段输入输出和首个 rejection/非法迁移；Exception、报告、project tool 与 Gizmo 必须引用同一不可变证据产品，不能各自重算或复制另一套事实。
- 连续几何、概率、搜索或优化问题在生产实现前依次完成：定义变量、单位与坐标系；把权威判定写成方程、不等式和事件边界；求定义域、开闭边界及可行域连通分量；让可视化消费同一分析产品；声明目标函数、次级目标与 tie-break；证明算法的完备性、精度、最坏时间/空间复杂度、分配和主线程预算。可由公式排除的设计不得留到运行实验才发现，固定步长、加密采样或随机试探不能冒充连续域解法。
- 任何包含两个以上数据相关循环/递归轴、穷尽搜索、事件或几何枚举、图遍历、全量 Asset 扫描、逐项昂贵 owner 调用，或可能形成笛卡尔积的 production、probe、测试、Gizmo、Editor tool 与离线计算，在首次可执行写入前必须形成一份可核对的 `Static Cost Ledger`。账本必须出现在当前任务的写入前进度记录、设计文档或项目要求的 checkpoint 中；只有渐进复杂度符号、口头声称“有界”、平均值、当前样本耗时或预期提前退出均不构成账本。
- `Static Cost Ledger` 必须逐项列出：每个循环/递归/队列/事件轴的符号、来源、上界公式及当前冻结输入的数值最大值；真实嵌套和乘积关系及最坏总迭代数，不能只分开列维度；每次迭代内 DDA、Physics、序列化、反射、AssetDatabase、materializer 或其他昂贵 owner 的最坏调用数及累计次数；分配对象数、字节上界、生命周期、峰值同时存活量和 retained cache；线程归属、同步点、主线程连续占用上界；复用/空间索引/缓存的唯一 owner 与失效条件；预算来源、预算数值和明确 `pass/fail` 结论。
- 账本中任何轴、单次成本、乘积、分配或同步主线程上界未知，或数值上界超过声明预算时，结论必须是 `fail`，并在写代码前改换算法或职责边界。不得先实现、编译、进入 Unity、运行测试/Profiler 或交给用户实验来补齐静态上界；性能实验只能在账本 `pass` 后测量静态分析无法确定的常数与集成开销。明显的无界搜索、全域笛卡尔积、候选内重复全量证明和可由共享 producer 消除的重复计算必须在该门禁直接淘汰。
- 写入后的每个新增循环、递归分支、任务分片、缓存和昂贵调用必须能一一映射回已通过的账本条目。实现结构、嵌套关系、输入域、线程、缓存生命周期或 owner 调用变化会立即使账本失效；继续写入或执行前必须先更新并重新判定。编译通过、单次快速样本、低平均耗时、异步化或主线程暂时流畅都不能替代或恢复失效的静态审计。

## 复用、迁移、兼容与抽象

- 实现前搜索并审查已有组件、接口、数据产品、触发器、Prefab/场景接线、配置、序列化字段、测试和文档。现有职责能完整表达需求时直接组合或小幅泛化复用，禁止复制状态、生命周期、订阅、控制路径和业务规则。
- 抽取协作者、接口或策略必须有当前真实的独立状态、生命周期、权限、稳定契约、变化轴或多个真实消费者；不得为假想需求预建框架，也不得为消除表面相似而合并语义不同的 owner。
- 修改契约时同步更新全部直接 producer、consumer、测试、序列化接线和仍有效的文档。迁移完成后删除旧入口、字段、事件、配置、适配器、别名、注释和一次性代码，不保留调用者自行选择的新旧双轨。
- 兼容性默认关闭。除非用户在当前请求中明确点名需要兼容的对象与边界，否则只实现当前权威契约，不主动考虑、设计、保留或测试任何向后、向前或跨版本兼容；历史需求、旧实现、已有 shim、潜在外部用户、未受控数据及“以后可能需要”都不构成兼容授权。
- 默认把受控 producer/consumer 同步迁移到当前契约，并删除旧 API、route、schema、响应字段、序列化字段、配置、ID/名称、历史行为、旧 package/server revision 适配，以及仅服务旧契约的 adapter、alias、wrapper、fallback 和迁移入口；不得为旧存档或数据形态保留兼容读写/转换路径。本条不授权删除用户数据，只禁止无明确要求的兼容实现。若用户本轮明确要求兼容，只实现其点名范围，并记录权威 owner、具体 consumer、期限或退役条件及对应验证，不得外推到相邻版本、平台或数据；点名兼容也不授权运行时 fallback，每个受支持目标必须在其边界拥有唯一权威实现。
- 唯一无需用户在每次任务重新点名的常设例外，是用户维护且面向多个 Unity 项目复用的通用 package/plugin/Editor extension 对其权威声明支持的 Unity 版本做版本兼容；该例外严格按共享 package/plugin 细则执行。除此之外，项目规则或专项细则不得新增常设兼容义务；发现旧条款时按用户当前要求删除或收紧，不能把它当成更具体的有效例外。
- 命名使用项目既有领域词汇并表达责任、方向、单位和失败语义。`Manager`、`Helper`、`Util`、`Common`、`Data`、`Temp` 等泛化名称不得掩盖多项职责；注释只说明代码无法表达的原因、硬约束和反直觉取舍。
- 新增或修改的源代码与脚本文件末尾只保留一个正常 EOF 换行，不得留下多余空行。

## 缺陷族处理

- 在用户已放入范围的系统、数据或工具中，一旦错误日志、最小复现、公开契约矛盾或权威状态确认真实 Bug，该 Bug 成为当前最高优先级实现项，即使它不是最初症状；先暂停依赖该缺陷的后续功能，按本文件闭合并修复，再恢复原任务。独立 owner 必须建立独立证据链，但不得仅以“与主症状不同”为由推迟。此优先级不扩大破坏性操作、外部协调、产品行为或验证权限；需要新权限时报告精确阻点。
- 功能恢复只是最低要求。发现缺陷后先暂停围绕最新症状继续加补丁，统一审查同一权威、机制、生产路径或直接数据流上的全部入口、同类实例、Variant、现存防御/fallback、冗余状态、状态迁移、consumer 和相邻失败模式，并把防御分支及其状态纳入删除范围。
- 修复应落在最窄的共享 owner、producer 或契约边界，同时覆盖报告实例、已确认同源实例、反例与产生流程；不得只在一个 consumer 增加特判，也不得借同源审计扩张到无关模块。
- 已经取得可复现的具体输入、暂停帧状态、不可变产品、事务记录或精确调用参数，并且测试/probe 边界能够只读调用真实生产 owner 时，首个取证动作必须是对这一条 exact witness 做确定性顺序回放。回放严格复用该版本实际经过的生产入口、producer、admission、publication/adoption 和 consumer，不另写同义算法；逐阶段保存权威输入、输出、owner、revision/context、状态迁移与拒绝理由，并在该 witness 的第一个非法产品、非法迁移或 rejection 处结束。完成这条回放前，不得先扩大为全 candidate 扫描、全路线/调用链枚举、随机采样、参数或排序实验，也不得用散落的 `Debug.Log` 代替可关联到同一 witness 的结构化阶段记录。
- exact witness 优先只规定诊断顺序和第一个失败边界的定位，不把单个 candidate、实例、分支或事务升级为系统根因，也不授权生产补丁。定位后只按该失败边界扩展闭合 owner、状态组合、同源入口和竞争解释所必需的最小证据，并继续满足本节的冻结版本、独立场景、完整状态矩阵与传播链要求；因此“先算这一条”与“完整矩阵后统一归因”必须依次执行，不能互相替代。若故障依赖时序、多 owner 交互或尚无可复现精确输入，先在最窄权威边界建立结构化捕获以取得真实 witness，不得伪造输入、重实现生产语义或用无边界的广泛扫描填补缺口。
- 新症状、新失败或新非法状态会使当前局部方案退回未验证假设。首份失败证据只能证明当前版本不通过，不能授权立刻修改下一处代码。若同一版本仍有相互独立且已获授权的入口、状态组合或场景可安全取证，先冻结本轮可执行实现与测试语义，完成这些证据后再统一归因；只有依赖非法前置的路径才停止。不得在只观察到最早失败边界时把它直接写成系统根因并进入下一轮补丁。
- 多入口、多状态、时序、publication/adoption/CAS 或有界搜索缺陷，在修改前必须建立可核对的组合证明：区分一项证据究竟只覆盖单个 candidate、实例、分支、事务还是全部输入；为每个必要合法状态写明进入事件、唯一 writer、退出迁移和单调量，为每个非法组合指出哪个 producer 或迁移能够构造它并从源头消除。不得为非法组合新增 guard，也不得保留只服务该 guard 的状态。只检查最新失败行、一个 consumer、一层调用栈或一个文件，不构成完整审查。
- “已找到根因”是证据结论，不是对最新失败行的命名。下结论前必须同时给出可构造前置、唯一 owner、发生错误的精确迁移、覆盖全部相关入口和状态组合的传播链、若修正该迁移应消失的反例，以及已排除的竞争解释；缺任一项只能写“待验证假设”。失败 tick 前移或后移、单一场景改善、异常换位置、更多 candidate 被访问、局部计数变化或日志更详细，都不能升级为根因证据。
- 严禁把不改变非法状态可构造性的改动当作修复，包括：调整 comparator、排序、tie-breaker、优先级或循环顺序；修改阈值、horizon、budget、candidate/beam 数、cadence、timeout 或延迟；增加 cursor、flag、enum、mode、缓存、snapshot、pending 状态、类型或“契约”名称；移动异常、断言、guard 或失败边界；隐藏、禁用或改写诊断；把局部补丁重命名成架构。只有该顺序、参数或状态本身就是已证明的权威产品事实，且完整组合证明显示改动从 producer 处消除了非法迁移、所有其他合法顺序也无法重建它时，才可进入修复；“跑得更久”“更晚失败”或“刚好选到可行分支”一律视为症状搬运。
- 对声明为有限、穷尽或可恢复进度的搜索，candidate 排序只拥有性能和确定性，不拥有正确性。若同一候选集合在未穷尽前因 sibling 顺序不同而改变成功/失败，先审查搜索进度是否被重置、deadline 是否消耗执行 runway、publication/pending 是否阻止下一事务、局部 rejection 是否错误提升为 candidate set/branch/transaction 失败；不得先改排序、权重或 candidate 数。只有明确非穷尽的产品策略才可让排序决定语义，且该裁剪必须在权威契约和验证矩阵中显式证明。
- 时序、调度与 publication/adoption/CAS 缺陷的组合证明必须覆盖 predecessor/current/successor 产品和 `absent -> planning -> ready/scheduled -> pending -> adopted/active -> retired/cancelled` 的所有可达阶段；逐项记录进入事件、唯一 writer、不可变来源、revision/context tuple、deadline 或资源消耗、取消/失效条件、CAS 失败语义及下一阶段活性。既要证明每个合法组合可达、可退出、不会空转，也要证明每个非法组合不能由任一 tick 顺序构造。只列状态名、只看 active 产品、只检查发布端或消费端，都不构成时序闭合。
- 把原子计算改成跨 tick、异步、分帧、增量或可恢复事务，会新增真实生命周期和 publication 时序，属于正确性设计变更而非单纯性能优化。修改前必须重开上述完整状态证明；修改后在用户已授权的范围内先用同一冻结 build 重跑受影响正确性矩阵，再取得性能证据；未获授权的验证准确标记为未验证。不得以耗时降低、帧率提高或预算受控跳过 motion/data/lifecycle 契约，也不得借本条扩大验证权限。
- 被新证据否决的实验性排序、参数、状态、接口、分支和诊断必须在尝试下一假设前撤回；不得把多个未证实实验叠加成新的默认系统。一次 coherent 修复必须在同一权威边界消除全部同源入口的非法迁移，并同步删除因此失去用途的 guard、fallback、状态和测试；只把首个失败推到下一层不算完成一轮修复。
- 单个场景应在首个非法状态立即结束，避免污染后续证据；整轮缺陷审查不得因此停止。冻结版本上其余独立且在范围内的诊断或验收必须继续，之后按共享 owner、机制和契约合并失败族，再进行一次 coherent 修复。不得强行延续非法状态、伪造有效前置、增加 fallback，或借完整取证运行范围外测试。
- 局部指标、截图、单次成功、编译通过或测试通过都不能替代结构正确性。只有职责与权限更清晰、生产路径无法重建同类缺陷，并且授权范围内的相关行为和相邻回归成立时，才可宣称对应范围完成验证。

## 交付前静态自审

- 修改 Unity 项目、package 或 plugin 的代码或编译契约后，必须执行 `unity-editor-safety.md` 的强制编译门禁；编译失败是当前实现的一部分，修复后重新编译到 error 为零。不得把“验证未授权”用于跳过编译，也不得把编译成功扩写成运行时、构建、序列化或视觉通过。
- 对命中 `Static Cost Ledger` 的实现，交付前必须重新逐项核对当前 diff 的循环、递归、任务、缓存、输入域和昂贵 owner 调用均映射到最新账本，账本数值仍为 `pass`；缺失、过期、只写渐进复杂度或无法覆盖当前实现时，静态审查失败，不能用已经完成的编译或运行结果放行。
- 对完整 diff 和直接 producer/consumer 链检查：唯一权威、职责与依赖、重复规则、必要状态及其唯一 writer、可推导/重复状态、分支复杂度、生命周期、错误暴露、API/序列化面、命名与单位、死代码、临时诊断及相邻回归。
- 确认没有 fail-close、防御性代码、fallback、内容特判、手工同步、隐藏调用顺序、任意延迟、重试、吞错、无 owner 的 TODO、注释掉的旧实现或只压住症状的 guard；发现既有项时已修正 producer/契约并同步删除相关分支、字段和测试。
- 对每项 comparator/排序/优先级/参数/budget/cadence/新增状态或类型改动，逐项指出它对应的权威产品事实和反例证明；无法证明者从 diff 删除。确认没有仅改变失败位置、发生概率、采样可见性或运行时长而保留同一非法状态的改动，也没有被否决实验残留。
- 确认改动覆盖当前职责和同源实例但没有扩张到无关模块；未获准运行的验证必须准确标记为未验证，不能因验证受限而省略静态质量审查。
