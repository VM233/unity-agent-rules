# Git 分支、提交与发布通用细则

## 适用范围与权限

- 创建、切换、合并、重命名或删除 Git 分支/worktree，提交、推送、删除远端引用或创建 PR 时读取本文件。
- 用户当前明确要求和消费项目根 `AGENTS.md` 决定允许的提交、推送、合并、删除与发布范围。本文件不把实现、验证、脏工作树或工具能力解释为新增 Git 权限。

## 默认分支策略

- 除非用户在当前请求中明确要求，不得创建、建议创建或为了隔离工作而切换到额外分支、worktree 或 PR 流程；默认只在已经检出的分支上工作。
- 脏工作树、并行任务、改动规模、提交或推送请求、审查便利、分支名前缀、宿主提供的 PR/branch 功能及“通常最佳实践”均不构成建分支授权。普通 `commit`、`push` 或 `push all` 也只作用于项目规则允许的已检出分支。
- 消费项目可以进一步声明唯一允许的分支，例如只允许 `main`。该项目约束会收紧共享默认值；不得用“当前已经在其他分支”放宽它。

## 已有分支与工作树保全

- 发现用户未要求的已有额外分支时，不再创建中转分支。先核对本地/远端引用、merge-base、未提交及未跟踪内容、上游和独占提交，再按用户当前要求或项目常设规则处理。
- 合并、切换或删除前必须保全当前 worktree。不得用 `reset --hard`、强制 checkout、覆盖文件、丢弃未跟踪内容或把用户改动藏入未说明的临时分支；能快进时优先快进，不能快进时保留清晰的合并边界。
- 删除分支前确认其需要保留的提交已能从目标权威分支到达。远端删除只在用户当前明确要求，或消费项目已有明确的单分支常设规则且本轮正在执行该清理时进行。

## 提交、推送与 PR

- 提交和推送通常是独立权限；只要求 `commit` 不授权推送。用户明确要求 `push`、`推送` 或发布到远端时，该结果请求授权为当前请求链完成必要的暂存、提交、远端同步、可确定冲突解决、推送和远端引用核验；只暂存当前请求或项目明确授权的范围，保留其他脏改。只有用户明确说 `push all` 或等价表述时才把完整 worktree 作为发布范围。
- 推送前先 fetch 目标远端并比较本地 HEAD、上游和远端目标引用。远端领先、分叉或 non-fast-forward 拒绝不能成为停在本地提交的交付点；在项目允许的已检出分支上审计双方提交和路径重叠，保留无关 worktree 内容，按权威 owner、producer/consumer 与产品契约解决冲突，重跑被合并失效的必要验证，然后继续推送。不得用整文件 `ours`/`theirs`、强推或历史重写代替语义合并，除非用户当前明确授权对应破坏性操作。
- 只有冲突确实需要尚未提供的产品选择、远端权限/保护规则阻止写入、必须获得破坏性历史操作授权，或相关 dirty 内容无法无损保全时，才停止并报告精确阻点；不得把“存在冲突”“已经本地提交”或“本地领先”表述为 push 已完成。
- 未经用户当前明确要求，不创建 PR，也不为了 PR 创建分支。用户只要求提交或推送时，直接作用于项目允许的已检出分支。
- 操作完成后读回本地分支、远端 heads、目标分支 HEAD、worktree 和上游状态。明确 push 的完成判据是远端目标引用可达且指向本次发布的本地提交，并且本地不再仅领先该远端；必须以 `git ls-remote` 或等价的远端读回核对 commit，不得只凭本地 tracking ref、单次 Git 命令返回成功或本地提交存在宣称完成。
